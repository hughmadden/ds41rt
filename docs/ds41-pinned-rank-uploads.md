# Overlap rank-plane uploads with response collection

The native FFN collector now copies arriving response chunks into a reusable pinned arena and enqueues H2D transfers on its reduction stream. Validated chunks occupy disjoint rank/row ranges, so their transport frames can be released immediately after the CPU staging copy. The arena holds up to eighty rows for four ranks: at most 3,276,800 bytes per wave, allocated at wave creation. Larger requests retain synchronous uploads.

The final TP4 reduction follows the uploads on the same stream and drains before publishing output. An upload guard drains on cancellation or early error before pinned storage can be reused. On success the reduction's existing drain satisfies that obligation, avoiding a second synchronization. The completed shared-expert output is now passed directly to reduction under its existing borrow, removing its redundant device copy. Wire format, rank accumulation order, GPU reducer and Spark execution are unchanged. This still stages through host memory; it is not direct GPU ownership of registered RoCE receive slots.

The GPU test `pinned_rank_uploads_match_sync_and_drain_on_drop` compares interleaved chunk uploads and final reduction against synchronous upload results for rows 1/6/80/81. Every byte matches. It also drops the guard after one queued upload, with and without an injected rank-bounds error, immediately overwrites staging, and verifies the already-submitted GPU data. This exercises the destructor's drain obligation; it is not a C16 scheduler test. Release daemon and test builds pass.

Both live APIs pass arithmetic JSON, streaming counting/usage, cancellation recovery and unsupported sampling rejection. All eight paired quality prompts preserve exact text and usage against the preceding mHC deployment; all six objective checks pass. Earlier broad numerical-quality gates remain open.

One-row host upload-call time falls from 21 to 7 µs and the 6 µs shared-output copy disappears. Six-row upload-call time falls from 31 to 12 µs. **These are host callback durations, not GPU DMA intervals.** The async callback measures staging and enqueue; the final reduction timer includes stream completion. Total collection median changes only 217→215 µs for one row and 554→552 µs for six rows. Receive/wait time correspondingly grows because the collector reaches its next wait earlier. Much of the previous copy work already overlapped remote execution.

The first three-stream comparison appeared slower (median target 27.42→26.85 TPS, dSpark 95.32→93.56). Restarting and retesting the previous and candidate binaries produced target 26.83→26.91 and dSpark 94.38→95.00. Thus no repeatable throughput regression or established throughput gain follows from these short uncontrolled-clock runs. The demonstrated improvement is less host blocking; C16 overlap benefits remain unmeasured.

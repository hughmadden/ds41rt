# Batch small router downloads into pinned staging

Router waves now allocate a reusable pinned staging buffer for up to eighty rows (5,328 bytes per row, at most 426,240 bytes per wave). The completed FP8 activation, expert IDs and routing weights download on the router stream, followed by one drain and copies into the owned wire request. Partial enqueue failures also drain before staging can be reused. The output borrow retains its owning wave; overlapping access to its staging is forbidden by the unsafe contract. Device allocations, graph addresses and wire encoding are unchanged.

Ordinary pageable destinations did not benefit from grouping asynchronous copies. Alternating isolated native-ABI measurements with 200 samples per path showed pinned staging, including the final host copies, reducing one-row download time from 17.08 to 9.55 µs, six-row from 17.91 to 9.77 µs, and eighty-row from 36.43 to 23.98 µs. At 4096 rows the extra host copy regressed 804 to 1278 µs, so requests above eighty rows retain the original direct-download path. This is a measured small-batch optimization; eighty is not a proven globally optimal crossover. The Python harness adds dispatch overhead and is not an isolated CUDA-event measurement.

The official-weight router reuse test passed 166 comparisons across all forty layers for rows 1 and 80, plus layers 0/20/39 for 4096 rows, with two rebinding cycles. The test now compares all three downloaded byte arrays against synchronous copies from independently executed fresh router owners. Existing graph reuse, finite-output and invalid-row recovery checks pass. Both release daemon and test executable build successfully.

Both live APIs pass JSON arithmetic, streaming counting/usage, cancellation recovery and unsupported sampling rejection. All eight paired quality prompts preserve exact text and usage against the preceding mHC-chain deployment. These bounded checks do not close earlier broad numerical-quality gates.

Live one-row routing/request preparation median falls from 50 to 41 µs; six-row falls from 62 to 49 µs. Baseline timing logs include earlier requests from the same executable, so sample counts differ. Three fresh sequential counting streams measured target TPS 24.59/24.90/24.69 before and 24.70/24.83/24.73 after. Speculative TPS was 80.00/85.04/86.12 before and 85.86/89.05/88.65 after. Clocks were not controlled; target throughput is effectively unchanged in these short runs, and the speculative difference cannot be attributed entirely to this edit.

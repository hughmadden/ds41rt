# Three-stage dSpark transformer chain

`DsparkChain` owns three independent transformer stages and a parent stream. One graph executes all attention/mHC/shared-and-routed-FFN operations and carries each stage's residual and shifted pre-mix to the next with ordered device copies, without host synchronization between stages. Expert dispatch and final route reduction now accept the containing stream; standalone expert and stage APIs retain their original owned-stream behavior.

Before metadata upload, all three stages validate their leases and expected committed ends, and the chain requires distinct cache owners, equal batch lengths and matching logical request IDs/positions in each packed row. Capture stores the three unique owner IDs and request count; replay checks them before launching. Failed validation clears publication, submitted work is drained before error return or destruction, and no child can outlive its borrowed weights. The graph retains stable device addresses, while request bindings and positions can change between replays.

The complete graph passed on both RTX PRO 6000 GPUs at 1, 3 and 16 requests with two input/position cases each. Final residual bytes and pre-mix bytes match separately synchronized stage-by-stage execution exactly. The changed case reverses request order, advances all three committed caches and uses cancellation-heavy input streams. Initial warmup is unpublished, duplicate capture and insufficient budgets are rejected, and invalid bindings cannot expose old output. Tests cover repeated cache owners, cross-stage request reorder, mismatched batch counts, stale committed ends, valid recovery and replacement cache owners that otherwise satisfy the request contract. All three committed rings remain byte-identical through draft execution.

After stream parameterization, the 18 independently reference-derived complete-stage cases also pass bitwise on each GPU, retaining nonzero attention, shared FFN and routed-expert contributions plus distinct shifted pre-mixes. The chain comparison establishes composition and stream-ordering correctness relative to those stages; it is not an independent full-model oracle or a real-checkpoint GPU numerical test.

Standalone chain device allocations total 62,157,516 bytes at one request, 64,154,556 at three and 228,906,468 at sixteen. These replace the three existing stage owners and add no device buffers; the partial two-wave dSpark device estimate remains 8,853,577,584 bytes, excluding shared vocabulary weights and driver/graph allocations. Device-copy fusion and redundant standalone child stream removal remain possible optimizations, with no throughput claim from this qualification.

The daemon and temporary fixtures build successfully. Native kernels are unchanged, using the current AOT library and b12x master pin. The chain accepts initialized embedded residuals and pre-mix; shared embedding production, final vocabulary/Markov/confidence head wiring, target verification/acceptance/rollback and production serving remain incomplete. The reusable stage evidence remains in `docs/ds41-dspark-stage-qualification.md`, and the temporary composition driver lives under `/tmp/ds41-chain/` using the existing sparse stage fixture.

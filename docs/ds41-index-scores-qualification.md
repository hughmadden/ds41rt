# Native paged index scores

`ds41rt_v41_index_scores`, exposed through `V41IndexScores`, scores explicit logical candidate rows from committed paged index history. Inputs are 32 FP4/E8M0 query heads of width 128, BF16 head weights, packed cache values/scales, U32 page tables, U64 committed row counts, per-query `(slot, causal_rows)` metadata and candidate row IDs. The head weights must already include the reference's `head_dim^-0.5 * n_heads^-0.5` factor. The output is FP32 storage of the reference's BF16 final scores.

The native operation decodes FP4 values with group-32 E8M0 scales, rounds decoded values to BF16, accumulates each dot in FP32, rounds it to BF16, applies ReLU, multiplies by the BF16 head weight with another BF16 round, then sums heads in FP32 and rounds to BF16. All 32 heads live on the RTX, so no index-head distributed reduction is needed. CUDA uses eight warps per candidate/query pair, four heads per warp and a final head reduction. It allocates no workspace and mutates no query or cache state.

Queries are bounded at 4096 and explicit candidates at 16,384, matching the official second-level budget of 2048 blocks of eight rows. The page-table stride is at most 4096, with up to 16 request slots and 16,777,216 physical rows. Invalid request slots, causal/committed/table bounds, sentinel positions and invalid physical pages yield negative infinity before key reads. Pointer spans are checked for null, alignment, overflow and output overlap. The Rust wrapper additionally checks buffer sizes and matching device IDs. Callers still validate request leases and serialize cache publication/release.

`scripts/qualify-ds41-index-scores.py` verifies the pinned `model.py` SHA-256 and extracts the actual two `Indexer.forward` scoring assignments into its oracle. It independently decodes packed values for the reference BF16 `einsum`, ReLU, weighted multiplication and head sum. All seven cases match exactly on each RTX PRO 6000 Blackwell: `(queries,candidates)` 1/3, 16/255, 80/511, 256/64, 4096/3, 1/4096 and 1/16384. Random packed codes use E8M0 scale bytes 123–127 with signed random BF16 weights. These exact comparisons establish the tested numerical range, not bitwise equality for every possible floating-point input/reduction order.

Cases cover mixed request slots, nonmonotonic page maps, malformed pages, empty committed histories, invalid query slots, causal masking, sentinel candidates and the last row of the maximum physical pool. Captured replay changes query values, weights, key values and page mappings; all-masked replay changes causal metadata. Shape/pointer/overlap guards are checked. The maximum query and candidate dimensions are tested separately, not as their largest Cartesian product. The largest pool uses 1,140,850,688 packed/scales bytes.

The real-weight compressor owner fixture still passes all 55 cases per GPU. Each of its four source-layer pool cases now invokes the Rust scoring wrapper against actual committed index buffers and device page tables after reuse creates logical pages in physical order `[1,0]`. Synthetic unit query heads and a single unit head weight make a CPU decoded-key sum an exact independent oracle. The consumer checks positions across the page boundary and rejects rows beyond the committed history. A captured consumer also reads changed causal metadata from the same allocation and returns all negative infinities. This qualifies consuming real-weight-generated keys; it does not qualify the model's query/weight projections, which remain unwired.

Native library, daemon and external owner fixture builds pass. Adjacent JSON records source/build/log hashes and primitive results. The reusable numerical qualifier is tracked; the extended owner fixture remains outside Git under `/tmp/ds41-compressor-owner`.

This is committed-history scoring, not complete sparse attention. Query projection/rotation/weight generation, causal proposal overlays, hierarchical candidate blocks, top-512 selection, FP8 KV storage, attention, production scheduling and throughput qualification remain open. Full-history scoring must be integrated with bounded score tiles/selection rather than materializing every query against the maximum history at once. No full-model or throughput claim is established by these component checks.

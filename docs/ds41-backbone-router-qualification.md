# Backbone routing and TP4 handoff qualification

`v41_backbone_router.rs` loads the official BF16 gate matrix and FP32 text/image correction biases for each backbone layer. Its captured wave consumes the block's normalized FFN input and image mask, computes sqrt-softplus scores, selects six of 384 experts using the appropriate correction bias, and normalizes unbiased selected scores with route scale 1.5. Both dSpark and backbone continue to use the existing native router kernel.

Each layer owns 3,935,232 weight bytes. Each wave owns 11,825 bytes per admitted row for BF16 hidden input, byte image mask, FP32 scores, six IDs and six FP32 weights: 946,000 bytes at 80 rows and 48,435,200 at 4096. Inputs and outputs use stable allocations, graphs recapture when live row count changes, and all work drains before output publication or free. Budget admission precedes allocation. Raw component results are unbound; `execute_ffn` validates the block layer, identity, row count, device and mask, then retains the execution identity and token positions.

The immutable `BoundExpertRequest` owns downloaded input and routing bytes, canonical six-route descriptors and a checked, monotonically allocated transport request ID. Its builder verifies scheduler token positions against the block, encodes the request and validates it with the same complete-batch parser used by Spark workers. Scheduler request identities and image spans must describe the actual input; full scheduler integration remains open.

`NativeTp4Wave::execute_ffn` accepts the bound request and matching RTX shared-expert output. It rejects missing/different binding, layer, rows, extent or device before dispatch; copies the shared contribution directly on the GPU; gathers the four TP planes; and returns a borrowed result retaining the block identity. Ordered reduction sums ranks in FP32, rounds each routed expert result to BF16, sums routes in FP32, adds the shared BF16 result and rounds the final result to BF16. The legacy host-shared entry point delegates to the same transport/reduction body.

Both RTX PRO 6000 GPUs passed 55 real-weight owner cases each: all 40 layers at 80 rows, plus capacities 1, 16, 256, 1024 and 4096 on layers 0, 20 and 39. Two independent waves matched byte-for-byte while borrowing one weight owner; changed-input and changed-image-mask replay, unpublished output, graph row mismatch and one-byte-short budget rejection passed. The 110 numerical sets per GPU matched the pinned official `Gate.forward` expert IDs exactly. Scores and routing weights passed rtol/atol 2e-5, with maximum absolute errors 7.152557373046875e-7 and 1.1920928955078125e-7 respectively.

A composed handoff fixture passed for layers 0, 2, 7, 8, 14, 20, 24 and 39 on both GPUs, each with 16 requests and five tokens per request. It runs real attention, shifted mHC, shared expert and routing; builds two differently masked requests; sends each identical frame to four local TCP peers; receives seven-row chunks; and checks every reduced BF16 coordinate against an independent CPU calculation. Invalid masks, incorrect token metadata and unbound shared results are rejected. Each encoded request gets a distinct transport ID. The block consumes the final reduced fixture result through its FFN finish boundary.

The four TCP peers return explicit analytical FP32 partials dependent on rank, route, coordinate and the received routing weight. **They do not execute routed expert weights or run on the Sparks.** This fixture qualifies request ownership, transport composition, reduction and block handoff. Real four-Spark MoE integration remains required. Routing on the actual block inputs passes a further 16 numerical sets per GPU, and final mHC passes eight sets per GPU using `qualify-ds41-block.py --ffn-result`. All 80 shared-expert payload hashes per GPU match the previously qualified shared-handoff vectors. The existing chained-BF16 coefficient sensitivity remains recorded by the block qualifier; it is not hidden by this integration.

`ds41-backbone-router-qualification.json` records the source, fixture, library, checkpoint and payload hashes, terminal build/run logs and numerical reports. Full-model execution, error/cancellation composition across the complete scheduler, real Spark execution of these generated routes, vision integration and speed targets remain unqualified.

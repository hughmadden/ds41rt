# Complete dSpark proposal graph

`DsparkWeights::draft` owns the complete proposal sequence on one captured stream: shared embedding lookup, three independent attention/mHC/shared-and-routed-FFN stages, final mHC collapse and RMS normalization, shared vocabulary projection, five dependent Markov corrections and samples, then raw confidence. It borrows the coordinator's embedding and vocabulary owners. The committed main-context KV producer remains separate and must finish before proposal execution.

A native allocation-free handoff transposes final residual and pre-mix from request-major `[R,5,...]` to the terminal's position-major `[5,R,...]` layout. The same seed buffer initializes the embedding and terminal anchors on every replay. Terminal suboperations now accept the containing stream; no host synchronization occurs between transformer stages and heads or between sampled positions. Existing standalone terminal execution retains its own stream.

Before enqueue, the owner validates seed count, prepared sampling count, the three independent cache owners, logical request order, leases and committed ends. Graph replay retains captured owner IDs and request count. Seed and sampling updates invalidate published results. Invalid sampling preparation also clears sampling readiness; valid preparation reserves request-owned Philox ranges, and cancellation consumes them. Replaying an explicitly prepared attempt reuses its draws. Returned tokens `[6,R]` contain the anchor and five proposals; corrected raw logits `[5,R,129280]` and raw confidence `[5,R]` retain position-major order. No target history or committed KV is modified.

Both RTX PRO 6000 GPUs passed complete-graph comparisons at 1, 3 and 16 requests with initial and changed-token/position/RNG cases. The changed case reverses packed request order and advances all three committed windows. All final residual/pre-mix bytes, sampled token bytes, corrected-logit bytes and confidence bytes match separate stage-by-stage execution followed by a separately synchronized terminal exactly. The baseline uses a CPU transpose, independently checking the layout connection. Outputs are finite with nonzero logits/confidence, valid vocabulary IDs and preserved anchors. Synthetic shared vocabulary, Markov and confidence weights are nonzero, and the batch includes greedy and stochastic temperatures. The native transpose separately matches PyTorch exactly for the same three request counts and changed-input graph replay on each GPU.

Guards cover insufficient budgets, unpublished warmup, duplicate capture, invalid and mismatched seeds, missing/invalid sampling state, repeated or replacement cache owners, cross-stage request reorder, mismatched counts, stale committed positions and valid recovery. All three committed rings remain byte-identical throughout proposal generation. Native layout guards reject invalid counts and overlapping outputs.

Device allocations for the complete draft owner are 76,544,868 bytes at one request, 90,539,396 at three and 333,274,980 at sixteen. These combine existing chain and terminal buffers; the transpose adds no workspace. The partial two-wave dSpark estimate stays 8,853,577,712 bytes, excluding shared coordinator tables and broader coordinator allocations. This does not establish full RTX memory fit or performance.

Native and daemon builds passed. Adjacent JSON records source, fixture and result hashes; temporary drivers live under `/tmp/ds41-draft` with sparse synthetic weights under `/tmp/ds41-stage`. This proves proposal graph composition relative to the separately executed components, not independent real-model numerical correctness. Target taps and scheduler wiring, confidence policy, target verification, acceptance/rollback, complete backbone attention, vision and serving qualification remain open.

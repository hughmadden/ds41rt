# Native RTX dSpark residency

`v41_experts::dspark::DsparkWeights` owns all three independent 128-expert stage sets and every remaining `mtp.*` tensor on the current coordinator RTX. Native FP4 experts use the existing packer; auxiliary tensors keep their official FP8, E8M0, BF16 or FP32 representation through bounded pinned staging. The backbone embedding and output head are shared by the reference and must be borrowed from coordinator residency rather than duplicated here.

Planning validates all stage placements and admits resident weights plus expert execution buffers for one or two waves before payload reads. Experts load serially before auxiliary tensors, so loading peak is packed expert residency plus one expert staging allocation. Each execution wave owns three independent stage workspaces, allowing distinct captured graphs without rebinding their weight addresses; the Rust borrow prevents weights from dropping before their executions. Callers account for every live wave using its selected capacity.

Static accounting from the official tensor template and current coordinator AOT manifest gives 7,219,445,760 bytes of packed experts and 713,428,872 bytes of auxiliary tensors. Capacity 80 covers sixteen requests with five draft positions each; its expert execution storage is 25,236,024 bytes per stage and 75,708,072 bytes per three-stage wave. Two such waves plus resident tensors require 8,084,290,776 bytes before attention caches, dense projection scratch/packed scales, shared backbone embedding/head, and CUDA graph/driver allocations. This is a partial allocation budget, not measured total GPU usage.

The daemon build passed with 447 warnings. No model load, GPU tests or placement benchmarks were run. Attention execution/cache ownership, native dense projection integration, Markov/confidence execution, sampling/verification, rollback and serving scheduler call sites remain unfinished; this owner does not yet execute a complete dSpark stage. Build evidence is in `ds41-dspark-residency-build.json`.

The V4.1 confidence path now borrows the final-stage BF16 projection weight and computes a raw FP32 dot product of collapsed hidden states and preceding-token Markov embeddings. Unlike the inherited terminal helper, it does not apply sigmoid. A dedicated native kernel fuses concatenation and input/weight promotion into the reduction. It uses a parallel FP32 reduction, so exact numerical equivalence to the reference GEMM has not yet been established.

`DsparkWeights::confidence` creates an owned per-wave hidden/embedding/output workspace. Producers write initialized, identically ordered rows into its stable BF16 inputs before execution; output is exposed only after completion. Capture warms the launch, records owned input/output and borrowed weight addresses, and replay enforces the captured row count. Destruction drains the stream and destroys the graph before releasing buffers. The new C/Rust entry validates row bounds and buffer sizes, with native alignment, extent and output-overlap checks.

Confidence storage adds 860,480 bytes per capacity-80 wave. Combined dSpark admission now includes this storage in addition to the three expert workspaces: two waves plus resident weights require 8,086,011,736 bytes before the previously listed exclusions. Callers still need to allocate each admitted expert/confidence owner and budget all live instances. The native library and daemon builds passed, and the confidence symbol is present in the shared library; no confidence numerical or graph runtime qualification, full container rebuild or full model execution was performed. The inherited terminal helper remains on the old serving path until migration.

`DsparkWeights::markov` now owns one draft position's token IDs, BF16 embeddings and FP32 vocabulary logits for 1–16 requests. It gathers the preceding-token embeddings, then projects through the native BF16 Markov head with FP32 accumulation/output. A dedicated native cuBLAS handle binds a fixed 4 MiB per-wave workspace; its device is checked on launch and its lifetime ends before workspace release. This avoids the inherited GEMM helper's thread-local handle. Captured graphs retain stable owned addresses and borrowed weights, with warmup before capture and exact row-count replay validation. The caller must supply valid token IDs, preserve each position's embedding for confidence, and serialize owner reuse.

A 16-request Markov owner requires 12,476,480 bytes including its explicit cuBLAS workspace. Combined admission now reserves that owner for each wave: two capacity-80 expert/confidence waves and two capacity-16 Markov owners plus resident dSpark weights total 8,110,964,696 bytes, excluding attention caches, dense scratch/packed scales, backbone shared embedding/head, full draft logits and sampling storage, and library/driver/graph overhead. The cuBLAS handle is initialized outside capture; internal library allocations are not covered by the explicit workspace budget.

Native shared-library and daemon builds passed, and all three Markov handle symbols are exported. Reference numerical agreement, graph replay and allocation stability are still unqualified. The five-position loop, shared-head logits addition, sampling and confidence embedding assembly remain to be connected; this is not a complete terminal head or serving implementation.

`DsparkWeights::terminal` now composes all five Markov/sample steps and the confidence projection on one owned stream. Inputs are upstream shared-head raw logits and collapsed pre-final-norm hidden states in dense position-major `[5,requests,...]` order, plus anchor token IDs, per-request temperatures and independent positive finite Exp(1) noise values per position/request/vocabulary entry. Each step adds Markov logits, writes corrected raw logits, samples the next token, retains its preceding-token embedding for confidence, and advances the Markov input without host reads. Greedy temperature zero chooses the lowest token ID on ties; stochastic sampling uses `logit/max(T,1e-5) - log(Exp(1))` argmax, which matches the reference sampling distribution mathematically but is not claimed to reproduce its finite-precision choices or RNG sequence.

One graph captures the complete sequence after warmup; it references exclusively terminal-owned inputs, outputs, child workspaces and borrowed resident weights. Shared logits and anchor inputs survive execution so capture warmup does not corrupt replay inputs. Child work is enqueued on the parent stream, which is drained before graphs, child handles or storage are destroyed. Output becomes visible only after synchronization, with tokens `[6,requests]` (anchor plus drafts), corrected logits `[5,requests,129280]`, and raw confidence `[5,requests]`. Live rows are densely packed rather than separated by capacity padding. Callers refresh noise and other inputs before reuse; this component does not commit request history.

At sixteen requests the complete terminal owner requires 137,446,208 bytes, including its Markov and confidence children. Combined dSpark planning now reserves these additions for each wave and at least eighty confidence rows; two capacity-80 expert waves plus two complete terminal owners and resident weights total 8,359,183,192 bytes. Attention caches, shared-head projection/norm buffers, native dense packing/scratch, backbone embedding/head residency and library/driver/graph allocations remain outside that partial budget.

The native library and daemon builds passed, and the draft-step symbol is exported. No numerical, sampling-distribution, graph replay or complete serving qualification was performed. Shared-head projection, upstream request-owned RNG population, verification/acceptance and scheduler integration remain unfinished; serving sampling extensions also remain to be connected. The inherited terminal serving path has not been replaced yet.

The terminal now generates sampling noise inside the draft-step kernel rather than accepting an external vocabulary-sized noise tensor. Core `DsparkRng` owns a request seed and a monotonic Philox subsequence cursor. Each draft reserves 1,280 subsequences (five positions times 256 kernel threads) before submission; cancellation consumes the range, and replay deliberately reuses it until a new attempt is prepared. All requests are checked for exhaustion before any reservation advances. This mapping depends on request seed/reservation, position and thread, not compact batch index, so moving a request between waves does not change its random stream. Equal explicitly chosen seeds and reservation indices intentionally reproduce draws.

`prepare_sampling` validates temperatures and request count, drains prior work, reserves ranges and uploads bounded seed/range and temperature metadata. Failed uploads invalidate sampling readiness and keep ranges consumed. Execute/replay reject missing or mismatched sampling state. External inputs are now only shared-head logits, collapsed hidden states and anchor IDs; producers no longer fill a noise buffer. The distinct `ds41rt_v41_draft_step_rng` symbol prevents accidentally binding the earlier external-noise ABI.

The CUDA sampler uses cuRAND Philox with strictly interior, exactly representable 23-bit uniform midpoints and transforms them into finite positive exponential values. Greedy rows skip RNG work. This is a finite-precision approximation to the reference exponential-race distribution; reference RNG sequence matching, distribution/tail checks, request-reordering reproducibility and graph replay remain unqualified. Request admission still needs to instantiate and retain RNG owners, and acceptance/history handling remains external.

Removing full noise storage and adding 16 bytes of RNG metadata per request reduces the sixteen-request terminal owner to 96,076,864 bytes (82,739,904 additional bytes beyond Markov/confidence). Two capacity-80 expert waves plus terminal owners and resident dSpark weights now total 8,276,444,504 bytes before the previously listed exclusions. Native and Rust builds passed with the RNG symbol exported; no GPU tests or full container rebuild were performed.

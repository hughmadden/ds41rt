# Native TP4 route transport and network execution

`V41BackboneRequest` validates complete revision-3 requests before execution: contiguous BF16 hidden rows of width 5120, six canonical row-major routes per token, valid backbone layers and expert IDs, unique experts within each row, finite nonnegative FP32 weights, and admitted row capacity. It preserves routing bits and order into caller-owned upload arrays. Legacy reduction/compression and streaming flags are rejected by this complete-batch adapter; their serving replacements still need integration.

Each response row contains six ordered FP32 [5120] route partials, represented on the wire as F32 output dimension 30720 and stride 122880 bytes. `V41Tp4Planes` borrows payloads in configured TP-rank order regardless of arrival order, rejects incomplete sets, duplicate/unknown executors, stale request/placement/layer identities and incorrect output geometry/dtype, and leaves assembly unchanged on rejection. All four ranks must receive the same canonical request, and in-flight wave request IDs must be unique within a placement version.

The daemon's `HostExpertExchange` and `ExpertExecution::execute_host_request` connect this contract to resident native backbone execution. Reusable host routing/partial buffers feed owned GPU inputs, the native kernel produces FP32 route planes, and a borrowed response prevents reuse of host output storage while encoding/sending consumes it. Layer, role, capacity and executor identity are checked before execution. This is the host-staged TCP fallback; device route views remain available for future RDMA transport.

The full transport suite passes 143 tests with one existing ignored test, including new canonical-route, FP32-bit-preservation, capacity, identity, dtype, duplicate and out-of-order assembly checks. Daemon compilation passes with 447 warnings, including entry points awaiting service integration.

A temporary worker executable using byte-identical production daemon modules loads synthetic official-shaped backbone layer 0 on four logical TP ranks: ranks 0/1 on ostrich and ranks 2/3 on dodo. Each rank owns its native prepared weights and execution storage. The RTX client sends identical M16 requests to all four ranks over persistent TCP connections, then validates responses in rank order 3/1/0/2 and uploads the four complete FP32 planes for native RTX reduction and shared-output addition. Two requests change hidden values, expert ordering and shared output. Both final outputs equal the independent full-intermediate-width-2304 K32 FP8/BF16 expert reference bit-for-bit; the relative-L2 < 0.01 and cosine > 0.9999 gates were retained. All four workers exited successfully after the two requests.

This qualifies real cross-host native TP4 arithmetic and wire transport on the two available physical Sparks, using synthetic checkpoint payloads. It does not qualify four physical Sparks, model output, production listener/bootstrap/scheduler integration, RDMA, chunked prefill/streaming responses, graph overlap across the network, or performance. Complete F32 route planes are larger than the old token outputs; large prefill batches must respect transport frame limits or use chunking/collectives. Exact source/fixture hashes, worker logs and results are in `ds41-native-tp4-network-qualification.json`.

Subsequent four-physical-host qualification using fresh native and current Rust fixture builds is recorded in `ds41-four-spark-tp4-qualification.md`; both M16 cases matched a freshly regenerated full-width reference bit-for-bit, while production listener/scheduler, streaming, RDMA and performance remain unqualified.

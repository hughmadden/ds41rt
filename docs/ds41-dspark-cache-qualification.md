# Committed dSpark window ownership

DsparkWindow owns one stage's 128-position KV ring for up to sixteen request slots, stable source/descriptor storage, bounded pinned metadata staging, and a captured native CUDA update graph. DsparkWeights::windows constructs the three independent stage windows; they are shared across alternating draft waves.

The kernel consumes normalized, RoPE-applied BF16 [rows,512] KV and reproduces the official K32 FP8 E4M3 quantization with UE8M0 power-of-two scales and the 1e-4 absolute-maximum floor, then rounds dequantized values to BF16 in the ring, matching the reference's in-place act_quant storage. Each update retains only a chunk's last 128 rows so longer chunks cannot race by writing repeated ring indices. Absolute positions and row-scaled addressing use 64-bit arithmetic.

Opaque leases carry owner identity, slot and generation. A complete batch is validated before GPU writes: active slots must be distinct, source spans valid, positions non-overflowing and appends contiguous. A first seed may begin at a nonzero position only if it supplies a complete 128-row tail. Releasing/reusing a slot invalidates old leases without clearing inaccessible ring rows. On a CUDA upload/launch/drain error, all affected leases are invalidated rather than exposing partially overwritten state; hardware fault injection remains unqualified.

Window views carry the committed end and valid row count. Their physical order is the reference order: attention reads indices 0..min(committed_end,128), followed by five draft positions in separate wave storage. The cache accepts only committed main-model KV; the caller still needs to enforce acceptance history and serialize readers/producers. Per-request positions can differ within one batch.

For sixteen slots and 4096 total source rows, each stage reserves 6,291,840 device bytes plus 384 pinned bytes, excluding graph/driver allocations. Three stages add 18,875,520 device bytes once across waves. DsparkBudget now includes this reservation, raising the partial two-wave capacity-80 total to 8,434,202,608 bytes; draft attention scratch, projections, shared vocabulary residency and remaining previously excluded allocations are still separate.

CUDA native and Rust daemon builds pass. A standalone Rust harness compiles the current production cache/memory owners and compares ring bytes against independently generated reference quantization on both RTX GPUs. Cases include sixteen mixed prefill chunks, lengths around and beyond the 128-row boundary, a seed position above 2^63, two-token batched appends, a one-slot update after a full batch, zero/tiny/normal activation groups, release/reuse and changed graph metadata. Every valid ring byte matches the reference bitwise. Duplicate slots, gaps, source bounds, position overflow, incomplete tail seeds, occupied/out-of-range slots, undersized budgets, stale generations and foreign owners are rejected; rejected batches preserve prior readable state.

The initial container invocation had an overlapping read-only mount and did not start; corrected mounts ran successfully, with exact hashes and final logs in ds41-dspark-cache-qualification.json. This qualifies committed cache storage and lifecycle, not dSpark attention computation: query/key projections, normalization/RoPE producers, attention/sink/output projection, private draft KV, full-stage sequencing and serving integration remain open.
